# Речь-презентация фреймворка

## Введение

Добрый день, коллеги.

Сегодня я расскажу о нашем фреймворке для автоматизированного end-to-end тестирования на базе Cypress и TypeScript. Сначала я дам общее представление о том, зачем создан этот фреймворк и какие задачи он решает, а затем подробно разберу его техническую структуру.

Фреймворк предназначен для повторного использования в тестовых наборах, которые работают с несколькими продуктами и окружениями. Он предоставляет единый подход к написанию тестов, управлению тестовыми данными, авторизации, работе с API, выбору продукта, фильтрации тестов и формированию отчетов.

У фреймворка есть пять основных целей:

1. Сделать тесты понятными для чтения.
2. Скрыть технические детали реализации из спецификаций.
3. Сделать тестовые данные предсказуемыми и переиспользуемыми.
4. Поддерживать несколько продуктов и окружений.
5. Предоставлять подробные артефакты при падении тестов.

Этот проект является шаблоном, а не готовым тестовым набором для конкретного приложения. Он задает структуру, правила и техническую основу, на которой можно строить реальное покрытие.

Главный принцип фреймворка - разделение ответственности.

Спецификация описывает, что должно происходить. Page Object знает, как взаимодействовать со страницей. Общие UI-механизмы находятся в базовом классе. API-запросы находятся в API-клиенте. Генерируемые данные создаются фабриками. Стабильные данные хранятся в фикстурах. Сквозные операции реализуются через пользовательские Cypress-команды.

Это разделение особенно важно потому, что тесты быстро становятся сложными для поддержки, если каждый spec-файл содержит собственные селекторы, шаги авторизации, API-запросы и логику подготовки данных.

Общий поток выполнения выглядит так:

```text
Spec
  -> Page Object
      -> Общие Page-хелперы
      -> Cypress-команды
      -> API-клиент и фабрики
  -> Cypress Runner
      -> Отчеты
      -> Скриншоты
      -> Видео
```

Спецификация описывает поведение, вспомогательные слои реализуют технические детали, а Cypress выполняет сценарий.

## Структура проекта

Основной тестовый код находится в директории `cypress`.

Директория `e2e` содержит спецификации. Они организованы по функциональности или назначению: smoke-тесты, навигация, framework-тесты, авторизация, поведение продукта и демонстрация фабрик.

Директория `pages` содержит Page Objects. Каждый Page Object представляет страницу или отдельную предметную область и предоставляет понятные действия, например:

```ts
examplePage.visit();
examplePage.verifyLoaded();
examplePage.verifyHeadingCount(1);
```

Директория `support` содержит общую логику фреймворка: пользовательские команды, авторизацию, настройки продуктов, API-клиенты, фабрики, очистку тестовых данных и общие assertions.

Директория `fixtures` содержит детерминированные тестовые данные и API-ответы.

Директория `scripts` содержит вспомогательные инструменты для проверки настройки проекта, обработки отчетов и запуска тестов для нескольких продуктов.

Директория `reports` хранит JSON-отчеты, HTML-отчеты, видео и скриншоты.

## Page Object Model

Фреймворк следует принципам Page Object Model.

Page Object скрывает селекторы и низкоуровневые Cypress-взаимодействия от спецификации. Например, страница продукта знает, где находится заголовок и как найти ссылки на документацию, но тест работает только с методами, описывающими ожидаемое поведение.

Селекторы отделены от действий страницы. Файл с locators содержит селекторы, а сам Page Object содержит действия и проверки.

Это означает, что при изменении селектора обычно достаточно обновить одно место, а не изменять все тесты, которые его используют.

Все конкретные Page Objects наследуются от общего абстрактного класса `Page`. Этот класс требует, чтобы каждая страница определяла URL и набор элементов.

Он также предоставляет общие защищенные методы:

```ts
element();
clickElement();
clearAndType();
verifyElementCount();
verifyUrlContains();
clickUntilNavigates();
```

Например, конкретный Page Object может вызвать `this.clearAndType()` и не дублировать логику очистки поля и ввода значения.

Базовый класс также определяет выбранный продукт и окружение. Благодаря этому Page Objects автоматически используют правильный base URL.

Здесь действует важное правило: базовый класс должен содержать только переиспользуемые механизмы, а не бизнес-логику конкретного приложения. Специфичные действия остаются в конкретном Page Object.

Спецификации также разделены по страницам и предметным областям. Тесты продукта используют `ExamplePage`, тесты авторизации используют `LoginPage`, а демонстрации framework-функций и фабрик используют `FrameworkPage`.

Каждый spec-файл создает нужные Page Objects в начале файла и повторно использует их в тестах. Благодаря этому сразу видно, с какой страницей работает спецификация.

## Фикстуры и фабрики

Фреймворк разделяет детерминированные и генерируемые данные.

Фикстуры используются, когда нужны стабильные и повторяемые значения. Например, fixture каталога всегда содержит один и тот же известный продукт. API-файлы содержат предсказуемые успешные и ошибочные ответы для stubbing.

Fixture можно загрузить так:

```ts
cy.fixture("products/catalog");
```

Фикстуры полезны, когда содержимое должно оставаться одинаковым во всех запусках.

Фабрики применяются, когда нужны уникальные или настраиваемые тестовые данные.

Сигнатура фабрики пользователей выглядит так:

```ts
export function createUser(overrides: Partial<UserData> = {}): UserData;
```

Фабрика создает полного пользователя со значениями по умолчанию, но тест может переопределить только нужное поле:

```ts
const admin = createUser({ role: "admin" });
```

Фабрика продуктов работает аналогично:

```ts
const unavailableProduct = createProduct({
  price: 29.99,
  available: false,
});
```

Сгенерированные продукты получают уникальные ID, а пользователи получают уникальные email-адреса. Это уменьшает вероятность конфликтов между тестами и делает подготовку данных компактной.

Factory spec демонстрирует оба сценария. Он проверяет, что продукты создаются с уникальными идентификаторами, что overrides работают правильно, а пользователи получают сгенерированные данные и нужную роль.

Общее правило здесь простое:

> Фикстуры используются для известных и стабильных значений, а фабрики - для уникальных и настраиваемых данных.

## API-клиент и очистка данных

Работа с API централизована в `ApiClient`.

Вместо того чтобы размещать `cy.request()` во всех спецификациях, мы используем типизированные методы:

```ts
api.getProducts();
api.createUser(user);
api.createProduct(product);
api.createOrder(order);
```

API-клиент знает структуру запросов и ответов приложения. Это повышает типобезопасность и скрывает технические детали API от теста.

Когда ресурс создается через API, фреймворк регистрирует соответствующий запрос на очистку. После каждого теста глобальная настройка запускает cleanup в обратном порядке создания ресурсов.

Обратный порядок важен, если ресурсы зависят друг от друга. Например, заказ может потребоваться удалить раньше, чем связанный с ним продукт или пользователь.

Очистка является best effort. Если удаление завершилось ошибкой, оно не заменяет исходную ошибку теста. Благодаря этому основная причина падения остается видимой.

Такой подход не позволяет тестовым данным бесконтрольно накапливаться в общем окружении.

Текущие API-примеры используют intercept и stub-ответы. Они демонстрируют архитектуру фреймворка, но не проверяют соединение с реальным backend. В реальном проекте API-клиент нужно подключить к настоящим endpoint-ам и контрактам ответов.

## Авторизация

Авторизация реализована через `LoginPage`, вспомогательные функции и Cypress-команды.

Фреймворк поддерживает несколько ролей:

```text
standard
admin
guest
teacher
student
```

Тест может авторизоваться через Page Object:

```ts
loginPage.loginAs("teacher", "/teacher/dashboard");
```

Также доступна переиспользуемая Cypress-команда:

```ts
cy.loginAs("student", {
  loginUrl: "/login",
  successUrl: "/student/dashboard",
});
```

Для кеширования состояния авторизации используется `cy.session()`. Благодаря этому Cypress не выполняет полный login flow каждый раз, когда состояние уже можно восстановить.

Credentials не хранятся в исходном коде тестов. Их можно передавать через `cypress.env.json` или через environment variables:

```bash
TEACHER_EMAIL
TEACHER_PASSWORD
```

Для стандартной роли также поддерживаются:

```bash
USER_EMAIL
USER_PASSWORD
```

Для нестандартных ролей общие credentials не используются как fallback. Если нужные данные отсутствуют, фреймворк выдает понятную ошибку.

Authentication-тест намеренно является opt-in. Он запускается только при наличии:

```bash
RUN_AUTH_EXAMPLE=true
```

Поэтому стандартный запуск не требует реальных credentials.

## Продукты и окружения

Фреймворк поддерживает несколько продуктов через единый product registry.

Каждый продукт определяет имя и base URL для разных окружений:

```text
dev
qa
stage
prod
```

Окружение выбирается через `ENV`, а продукт через `TARGET`.

Например:

```bash
ENV=qa TARGET=checkout npm run cy:run
```

Page Objects автоматически используют выбранный продукт, поэтому в спецификациях не нужно прописывать URL вручную.

Если сценарий относится только к одному продукту, тест может использовать product guard и пропустить себя для остальных продуктов. Это позволяет запускать общий набор тестов безопасно.

Фреймворк также поддерживает:

```bash
TARGET=all
```

Для неинтерактивных команд runner разворачивает `all` в список всех продуктов из product registry и запускает Cypress отдельно для каждого продукта.

Например:

```bash
ENV=qa TARGET=all TAGS=@Smoke npm run cy:run
```

Для каждого продукта создается отдельный процесс Cypress со своим значением `TARGET`. Запуски выполняются последовательно, а итоговая команда завершается с ошибкой, если хотя бы один продуктовый запуск завершился неуспешно.

Эта логика находится в общем runner-скрипте, поэтому она применяется к локальному запуску, debug-запуску, Cloud recording, smoke-тестам, navigation-тестам и запуску отдельных спецификаций.

Команда `cy:open` остается однопродуктовой, потому что открытие нескольких интерактивных Cypress-сессий одновременно не является практичным сценарием.

Сейчас в шаблоне зарегистрирован один продукт - Cypress Kitchen Sink. После добавления новых продуктов они автоматически попадут в `TARGET=all`.

## Cypress-команды

Пользовательские Cypress-команды содержат общую логику, применимую к разным страницам.

Примеры:

```ts
cy.dismissKnownOverlays();
cy.loginAs(...);
cy.createTestData(...);
cy.cleanupTestData();
cy.openInSameTab();
cy.storeValue(...);
```

Например, закрытие общих overlay-элементов не относится к одной конкретной странице, поэтому эта логика реализована как общая команда.

Фреймворк также позволяет менять поведение ссылок, которые обычно открываются в новой вкладке. Это полезно, потому что Cypress напрямую не управляет несколькими вкладками так же, как настоящий браузер.

Общие команды позволяют не дублировать технические шаги в Page Objects и спецификациях.

## Теги и выборочный запуск

Фреймворк использует Cypress grep tags для управления тем, какие тесты необходимо запускать.

Примеры тегов:

```text
@Smoke
@Framework
@Product
@Targets
@Factories
@Fixtures
@Api
@Auth
```

Тег можно комбинировать с выбором продукта:

```bash
ENV=qa TARGET=all TAGS=@Smoke npm run cy:run
```

Runner передает фильтр тегов в каждый продуктовый процесс Cypress. Это означает, что один и тот же набор smoke-тестов будет применен ко всем выбранным продуктам.

Доступны следующие режимы запуска:

```bash
npm run cy:open
npm run cy:run
npm run cy:debug
npm run cy:record
npm run test:smoke
npm run test:navigation
npm run test:spec
npm run test:all
```

`cy:run` выполняет локальный запуск в Chrome без записи в Cypress Cloud.

`cy:debug` включает подробное логирование Cypress и сохраняет вывод в `console_output.txt`.

`cy:record` включает запись в Cypress Cloud.

Команды `test:smoke`, `test:navigation` и `test:spec` поддерживают Cloud recording, группировку и параллельное выполнение.

`test:all` запускает все spec-файлы через Cypress Cloud в группе `all` с поддержкой параллельного распределения между CI-агентами.

Примеры:

```bash
ENV=qa TARGET=all TAGS=@Smoke npm run cy:debug
ENV=qa TARGET=all TAGS=@Smoke npm run cy:record
ENV=qa TARGET=all TAGS=@Smoke npm run test:smoke
ENV=qa TARGET=all TAGS=@Smoke npm run test:navigation
ENV=qa TARGET=all TAGS=@Smoke \
SPEC='cypress/e2e/framework/factories_features.cy.ts' \
npm run test:spec
ENV=qa TARGET=all TAGS=@Smoke npm run test:all
```

## Конфигурация и вспомогательные инструменты

Конфигурация Cypress определяет default base URL, reporter, размеры viewport, таймауты, запись видео, скриншоты при падении и настройки browser security.

Фреймворк использует Cypress grep для тегов.

Также предусмотрена поддержка iframe и реальных browser events через Cypress-плагины.

Mochawesome во время запуска создает JSON-данные отчета. Отдельные скрипты могут объединить эти результаты и сгенерировать итоговый HTML:

```bash
npm run report:clean
npm run report:merge
npm run report:generate
```

Локальные запуски хранятся в отдельных директориях для каждого run. Видео и скриншоты сохраняются как диагностические артефакты.

В проект также входят:

- TypeScript со строгой проверкой типов
- ESLint
- Prettier
- Cypress- и Mocha-правила для linting
- `ts-node` для TypeScript-скриптов
- Husky hooks
- Скрипты проверки настройки проекта

Основные проверки качества:

```bash
npm run lint
npm run typecheck
npm run validate-setup
```

Они помогают обнаружить проблемы со стилем, типами и отсутствующими файлами до запуска тестов.

Стандартная настройка проекта выглядит так:

```bash
npm install
cp cypress.env.json.example cypress.env.json
npm run validate-setup
```

Файлы с credentials и локальными настройками окружения не должны попадать в репозиторий.

## Cypress Cloud и CI

Фреймворк содержит команды для Cypress Cloud, но для полноценного Cloud-запуска проект еще нужно сконфигурировать.

Необходимы:

- Рабочий Cypress Cloud project
- `projectId` в Cypress-конфигурации или в command line
- Защищенный `CYPRESS_RECORD_KEY`
- Окружение, в котором эти значения доступны

В репозитории пока нет CI workflow. Поэтому отдельно потребуется добавить CI orchestration, browser matrices, управление секретами и загрузку артефактов.

Локальные команды `cy:run` и `cy:debug` не записывают результаты в Cypress Cloud. Для записи используются команды с `--record`.

## Текущие границы шаблона

Важно понимать, что этот проект является универсальным skeleton.

Все текущие product URLs указывают на демонстрационное приложение Cypress.

Стандартные селекторы также являются демонстрационными. В реальном приложении их нужно заменить на стабильные селекторы, например `data-testid` или `data-cy`.

API-примеры используют intercept и stub, поэтому они демонстрируют архитектуру тестов, но не подтверждают доступность реального backend.

Авторизация является opt-in, потому что в репозитории нет реальных credentials и полноценного login-приложения.

Setup validator проверяет наличие обязательных файлов, но не проверяет доступность браузера, корректность credentials, доступность продукта, настройки Cypress Cloud или достижимость приложения.

Также существует различие между URL, который использует Page Object для выбранного продукта, и относительными API-запросами. В реальной мультипродуктовой конфигурации global Cypress base URL должен соответствовать выбранному продукту, чтобы navigation и API setup обращались к одному и тому же приложению.

## Заключение

Подведем итог.

Фреймворк основан на нескольких устойчивых принципах:

- Спецификации должны описывать поведение.
- Селекторы и действия должны находиться внутри Page Objects.
- Общие механизмы должны находиться в базовых helper-классах.
- API-детали должны находиться внутри API-клиентов.
- Фикстуры должны использоваться для детерминированных данных.
- Фабрики должны использоваться для уникальных и настраиваемых данных.
- Credentials должны храниться вне исходного кода.
- Очистка тестовых данных должна выполняться автоматически.
- Продукты и окружения должны конфигурироваться централизованно.
- Теги и target selection должны управлять запуском.
- Отчеты и failure artifacts должны помогать понять причину проблемы.
- Кодовая база должна проверяться через linting, type checking и setup validation.

Главная ценность фреймворка в том, что он создает общий язык для автоматизации.‰

Новый тестировщик понимает, куда добавить новый тест. Разработчик понимает, где поддерживать селектор или API-контракт. CI-пайплайн понимает, как выбрать продукт, окружение, теги и execution group. А при падении теста команда получает достаточно данных, чтобы понять, что произошло.

Таким образом, задача фреймворка заключается не просто в запуске Cypress-тестов. Его задача - предоставить поддерживаемую, типизированную и расширяемую систему для построения надежного автоматизированного покрытия по мере роста продукта.
